# 2026-11-08 P0' 試作：NH＋多項式＋fmix64 の素朴版

## 目的

CONCEPT のゲート「速度目標と ε 目標を数値で決める」。Rust で素朴版を書き、
SMHasher3 の品質と速度を foldhash / ahash / XXH3 / rapidhash / CLHASH と比べる。

## 計測環境

- Intel Xeon @ 2.10GHz（AVX2・AVX-512F・PCLMULQDQ・VPCLMULQDQ・BMI2 あり）、4 vCPU、15GB。クラウド VM なので絶対値には揺れがある
- rustc 1.97.0、SMHasher3 `20260827-main-3b619371`、clhash `c35030a`

## 調査メモ

- SMHasher3 は Rust 製ハッシュ（ahash・rapidhash）を C++ に移植して取り込んでいる。LeanHash は実装を1つに保つため、Rust を staticlib にして C ABI でリンクする方式にする（FFI 呼び出しのぶん小さい入力の速度は不利になる → 小さい入力の速度は Rust 側ベンチで見る）
- SMHasher3 の `seedfn` は seed から鍵表を前計算してポインタを渡せる（`thread_local` 推奨）。NH の鍵（128 バイト以上）の展開を毎回やらずに済む
- clhash リポジトリのベンチは Java 風の単純なハッシュとの比較だけ。論文の比較（VHASH・CityHash 等）は別リポジトリにある。ここでは README の「Skylake で長い入力 0.1 cycles/byte」を TSC で測って照合する

## 試作1：素朴版（`rust/leanhash`、コミット時点の `hash_nh64` / `hash_nh32`）

### 設計

- ブロック 128 バイト。`Nh64` は 64bit 語 8 組の積（64×64→128）の和、`Nh32` は 32bit 語 16 組の積（32×32→64）の和
- NH 出力を **60bit** の limb に分けて多項式 mod p = 2⁶¹−1 の係数にする（`Nh64` は 1 ブロック 3 係数、`Nh32` は 2 係数）。最後に長さ（バイト数）を係数として足す
- 出力: `fmix64(((h << 3) | t>>61) ^ fin)`。t は NH 出力の上位語の和
- ε（同じ鍵で x≠y、n ブロック）: `Nh64` ≤ 2⁻⁶⁴ + (3n+1)/p、`Nh32` ≤ 2⁻³² + (2n+1)/p

### 書きながら気づいたこと（Lean で形式化するときの要注意点）

- **limb を 61bit にすると単射でなくなる。** 61bit の値 2⁶¹−1 は p そのもので、mod p で 0 と区別できない。60bit にした
- **多項式の出力 h は 2⁶¹ 未満なので、そのまま fmix64 に入れると出力が 2⁶¹ 通りしかない**（64bit 出力として見ると衝突が約 8 倍）。`h << 3 | (補助値 3bit)` は単射なので、衝突すれば h も衝突し、ε は変わらず値域だけ約 2⁶⁴ に広がる。Lean ではこの単射性も補題にする
- **0 埋めと長さ:** 端数ブロックを 0 埋めするので "a" と "a\0" は NH の入力が同じ。長さを最後の係数にすることで、長さが違えば差の多項式の定数項が 0 でなくなる（テスト `padding_and_length_are_distinguished`）
- **fmix64 の逆元を記憶から書いたら1つ間違えていた**（`0xc4ceb9fe1a85ec53` の逆元。正しくは `0x9cb4b2f8129337db`）。テストで検出し、Python の `pow(c, -1, 2**64)` で計算し直した。CONCEPT どおり、定数は外部で計算して Lean で検証する
- 鍵が漏れれば衝突は簡単に作れる（2 語目を −k₁ にすると積が 0）。テスト `leaked_key_gives_collisions` として残した。ε-AU の仮定「鍵が入力と独立」の確認

### 分析

- **長い入力:** 素朴版は XXH3 の 1/7（nh64）〜1/4（nh32）。1 ブロック 128 バイトごとに多項式段の mulmod が 2〜3 回**直列に**並ぶのが律速とみる（1 回 10 サイクル前後として 128 バイトあたり 20〜30 サイクル）。NH の乗算自体は nh64 で 128 バイトあたり 8 回で、こちらはパイプラインで流せる
  → **ブロックを大きくする**（VHASH・CLHASH は約 1KB）と多項式段の比率が下がる。代わりに鍵が大きくなる（CLHASH の鍵は 133 語 ≒ 1KB）
- **短い入力:** 3〜8 バイトで 26〜53ns と桁違いに遅い。端数処理で 128 バイトの 0 埋めと可変長コピーをしたうえに、mulmod を 4 回直列に回しているため。8 バイトが 16 バイトより遅いのは 0 埋めの memcpy 経路の差とみられる（未確認）
  → 短い入力専用の経路（0 埋めなし、mulmod なし）が要る。ハッシュ表の鍵の大半は短いので、ここが最重要
- CLHASH は README の「Skylake で 0.1 cycles/byte」に対し、この VM では 1 MiB で 20 GB/s。TSC 2.1GHz 換算で約 0.10 cycles/byte で、**論文側の値とほぼ一致**（cycles/byte の実測値は CSV に残す）

## 試作2：ブロック 1KB・短い入力の専用経路・SIMD（`rust/leanhash/src/v2.rs`）

試作1の分析から3点を変えた。途中の版（v2 / v2b）も比較のため残してある。

| 版 | ≤ 32B | 33B〜1KB | > 1KB |
| :--- | :--- | :--- | :--- |
| v2 | NH64（1組＋長さの組）→ multiply-shift → fmix64 | NH64（スカラー）→ multiply-shift | NH64 1KB ブロック → 多項式 |
| v2b | 同上 | 同上 | **NH32 Toeplitz 2本（AVX2）** → 多項式 |
| **v2c** | 同上 | **NH32x2（AVX2）＋長さレーン → multiply-shift** | v2b と同じ |

- **短い入力:** 0 埋めと memcpy をやめ、xxh3 風の重なり読み（1〜3B は先頭・中央・末尾の 3 バイト、4〜8B は先頭と末尾の 4B、9〜16B は先頭と末尾の 8B）。長さごとに単射。長さは NH の追加の組 (L, 0) として入れる
- **1 ブロック以内は多項式段を通さない:** NH の 128bit 出力を multiply-shift `hi64(m·acc mod 2¹²⁸)`（m は奇数の鍵）で 64bit に落とす。Dietzfelbinger の結果で 2⁻⁶³-AU。ε ≤ ε_NH + 2⁻⁶³
- **NH32 の Toeplitz 2本:** 鍵を 1 レーン（2 語）ずらした 2 本の NH32 で ε = 2⁻⁶⁴。同じデータを2回使うだけなので SIMD で安い（UMAC の構成）

### 試行錯誤

- **境界チェックで遅かった:** 添字で書いたループに境界チェックが残り、32B が 18ns かかっていた。`chunks_exact` と `zip` で書き直して 9ns
- **自動ベクトル化されなかった:** NH32 を `(x & M32) * (y & M32)` の形にし、固定長配列にして境界チェックを消しても、LLVM は vpmuludq を使わずスカラーの imul のままだった（`--emit asm` で確認）。CONCEPT の方針どおり `std::arch` の AVX2 組み込み関数で明示的に書いた（`_mm256_add_epi32` が u32 ごとの mod 2³² 加算、`_mm256_mul_epu32(s, s>>32)` が lo·hi）。スカラー版との一致をテスト `simd_block_matches_scalar`・`partial_simd_matches_scalar` で確認
- **VM の速度が実行ごとに最大 1.5〜2 倍揺れた:** 競合の値も同じように動くので、ハッシュごとに順に測ると比較が崩れる。計測器を「同じ入力長で全ハッシュを交互に 15 回測って中央値」に変え、`taskset -c 2` で 1 コアに固定した。以後は比率で比べる
- **未証明の点（P2 で証明する）:** 1 ブロック以内で組の数が違う 2 入力の NH の衝突確率。組数が同じなら NH の定理そのまま（2⁻⁶⁴）。組数が違うと、余分な組の積 (y+k)(y'+k') がある値 c に等しくなる確率になり、c = 0 のとき約 2⁻⁶³。全体で ε ≤ 2⁻⁶²（NH 2⁻⁶³ + multiply-shift 2⁻⁶³）と見込む。**NH32x2 の中間経路も同じ議論が要る**

### SMHasher3 への組み込み（`bench/smhasher3/`）

- `leanhash.cpp` が Rust staticlib（`rust/leanhash-ffi`）の C ABI を呼ぶ。鍵は seedfn で `thread_local` の配列に展開
- `build.sh` は上流のソースを別ディレクトリに複製して改変し、`SMHasher3-leanhash` をビルドする。最初は rsync 前提で書いたがコンテナに無かったので tar に置き換えた
- 静的リンクに要るライブラリは `cargo rustc -- --print native-static-libs` で確認（`-lgcc_s -lutil -lrt -lpthread -lm -ldl -lc`）
- v2c の健全性チェック（Sanity）は全 PASS。検証値は `0xAEF37E4F`

### 先行研究の追加：PolymurHash（調査の漏れ）

SMHasher3 の一覧で見つけた。foldhash と同じ作者（orlp）の、多項式 mod 2⁶¹−1 によるユニバーサルハッシュ。CONCEPT 5.2 の「見つからなかった」の一部（証明付き衝突上界と実用速度の両立）に、手書きの証明で既に取り組んでいる。

- 上界: n バイト以下の異なる 2 入力で衝突確率 ≤ n·2⁻⁶⁰·²（鍵は入力と独立が前提）。証明はリポジトリの `extras/universality-proof.md`（手書き、機械検証なし）
- 弱い鍵の注意（p−1 の小さな約数に対応する部分群）が README にある
- **LeanHash との差:** NH 段があるので、上界の長さ依存が小さい

| 入力長 | LeanHash v2c（見込み） | PolymurHash |
| ---: | ---: | ---: |
| ≤ 16B | ≈ 2⁻⁶² | ≤ 2⁻⁵⁶·² |
| 1KB | ≈ 2⁻⁶² | ≤ 2⁻⁵⁰·² |
| 1MB | ≈ 2⁻⁶⁴ + 3073/2⁶¹ ≈ 2⁻⁴⁹·⁴ | ≤ 2⁻⁴⁰·² |

→ 差別化の軸は「**機械検証された証明**」と「**長さに強い上界**」。速度は PolymurHash とも比べる（SMHasher3 の速度テストと Rust の `polymur-hash` クレート）

### 速度（SMHasher3 `--test=Speed`、`taskset -c 2`、1 本ずつ順に実行）

生データ: `bench/results/2026-11-08-smhasher3-speed/`。SMHasher3 の bulk は 256KB の入力（L2 に収まる）で、Rust 側の計測（2MB のバッファ上で開始位置をずらす）より全体に速く出る。「@ 3.5 ghz」は SMHasher3 が仮定する換算で、実周波数ではない。

| :--- | ---: | ---: | ---: |
| **LeanHash-v2c** | 30.2 | 10.2 | 1.00 |
| LeanHash-v1（素朴版） | 99.0 | 2.7 | 0.26 |
| XXH3-64 | 22.3 | 25.3 | 2.48 |

- LeanHash は FFI 越しの呼び出しなので、短い入力では数サイクル不利（C++ に移植された競合はインライン化される）
- **短い入力は PolymurHash と同等で、長い入力は約 1.8 倍速い**。XXH3 には長い入力で約 40%、短い入力で約 74%
- rust-ahash は SMHasher3 の C++ 移植（AES 版でもこの値）で、Rust ネイティブの ahash（Rust 側の計測では XXH3 に近い）とは大きく違う。ahash との比較は Rust 側の数字を使う
