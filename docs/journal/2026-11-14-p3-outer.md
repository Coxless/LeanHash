# P3 続き：核より外側（バイト読み・レーンのループ・経路の分岐）を Lean で組み、v2c の仕様と一致を証明する

## 目的

P3 の残り（[前回の journal](2026-11-10-p3-hashir.md) の「次にやること」1〜3）を片付ける。

- 核（`nh32_lane`、`nh_pair`、`horner`、`limb0..2`、`ms`、`finish`）を、Rust の `hash_c`（スカラー版）と同じ形で
  組み合わせた参照実装を Lean に書く。バイトの読み出し（`rd32` / `rd64`）、NH32×2 のレーンのループ、端数の重ね読み、
  完全ブロックのループ、`absorb`、経路の分岐まで
- それが仕様 `Props.hashV2c` と一致することを `sorry` なしで証明する（`eval fast = spec` を全体へ）
- 参照実装は Mathlib を読まずに実行できるようにして、Rust の `hash_c` と出力を突き合わせる（差分テスト）

## 方針（決めたこと）

- IR にループの文を入れるのはやめ、Lean 側で `List.foldl` で核を回す形にする（前回の選択肢 1 の後者）。
  外側の Rust（スライス・ループ）を形式的につなぐのは P3.5（Aeneas）の仕事として残し、ここでは
  「Rust と同じ形の Lean の参照実装 = 仕様」を定理に、「参照実装 = Rust」を差分テストにする
- 参照実装のファイル（`LeanHash/Impl/Outer.lean`）は Mathlib を import しない。バイト読みは仕様の
  `readLE`（Finset の和）ではなく `List.foldr` で書き、等しいことは証明側で示す
- SIMD（AVX2）版のブロック和は対象外（和の順序が違うだけだが、組み込み関数の対応表は別の作業）

### 参照実装 `LeanHash/Impl/Outer.lean`

- `KeysI`（Rust の `v2::Keys`：`nh : Fin 130 → BitVec 64`、`m : BitVec 128`、`r`、`fin`、`finMid`、`finLong`）
- 核の呼び出しは `laneI` / `pairI` / `hornerI` / `limb*I` / `msI` / `finishI`（どれも `Kernel.run` そのもの）
- バイト読み `rdLE`（再帰。`readLE_succ` と同じ形）、`rd64I` / `rd32I`
- 経路 A は `nh_partial` の L ≤ 32 で通る分岐だけを書いた（17〜32 は pairs = 2 で、本体ループは回らず「端数の組 p = 0」と「最後の組 q = 1」）
- 1〜3 バイトは Rust と同じく OR とシフトで組む（仕様は足し算。一致は証明側で示す）
- NH32×2 のループは `laneLoop`（`List.range n` の `foldl`）。完全ブロックは「レーン i は 8i から」、端数は「最後のレーンだけ末尾 8 バイト」
- 長い経路は完全ブロックの `foldl` → 最後のブロック（`lastBlockI`）→ 長さの Horner → `pack` → `ms` → `finish`
- Mathlib なしで `lake env lean LeanHash/Impl/Outer.lean` が 1.9 秒で通る

### 証明 `LeanHash/Impl/OuterEquiv.lean`（途中経過）

- `rdLE_eq`（`rdLE = readLE`）、`readLE_add`（a+b バイト = a バイト + 256^a·b バイト）→ `lane32_rd64`（8 バイト読みのレーン = 前 4・後ろ 4）
- `z64` / `z128`：u64 / u128 を ZMod (2³²)² / (2⁶⁴)² に写す。足し算を保つ（`z64_add`）
- `laneLoop_z`：ループの値 = Σ_{i<n} pairVal（`List.range_succ` で帰納法）
- `nhT_split`：仕様の Σ_{Fin 129} を「Fin 128 の部分 + 位置 128」（`Fin.sum_univ_castSucc`）に分け、
  Fin 128 の和を `Fin.sum_univ_eq_sum_range` で `range 128` に、範囲外（なし）を落として `range n` に
- 端数 `partial_nhT`・完全ブロック `full_nhT` は `nhT_split` の特殊化。位置 128 以外が `msgB b` と同じ M なら何でもよい形にした（`msgFull` / `msgLast` にもそのまま使うため）
- 経路 B `hashBI_eq`、経路 A `hashAI_eq` まで通った
- 詰まった所:
  - `rw [Fin.sum_univ_castSucc, Fin.sum_univ_castSucc]` が同じ和を 2 回分解した → `(n := 128)` を明示
  - `lanesB L` と、参照実装の中の `(len + 7) / 8` が混ざると `rw` が「motive is not type correct」（`if` の Decidable インスタンスが項に依存）→ 両方を `lanesB` を開いた形にそろえ、`split_ifs` + `omega`
  - `rw [← z128_val]` が乗数 m の `toNat` まで書き換えた → `z128_val (_ + _)` と位置を指定
- 1〜3 バイトの OR 組み立ては `Nat.two_pow_add_eq_or_of_lt` を 2 回で足し算に（`or3_toNat`。`bv_decide` は使っていない）

### 長い経路と全体（続き）

- `fullBlock_z` / `lastBlock_z`：ブロック j の参照実装の出力（z64 に写したもの）= `outL K s j`。最後のブロックは端数あり（`partial_nhT` を `tail s` に）と端数なし（`nhT_split` を n = 0 で）に分けた
- `absorb_foldl`：`absorb` の繰り返し = limb の列への Horner の繰り返し ＋ y の和（列に対する帰納法）
- `hashLongI_eq`：Horner の最後に長さを足した列が `hornerRun` で、既存の `hornerRun_eq`（係数 < 2⁶³）から `polyH` に。
  係数の上界は limb0/1 が 2⁶⁰ 未満、limb2 が 2⁸ 未満、長さが p 未満
- **主定理 `hashCI_eq`**：`K.r.toNat < p` と `s.length < p` のもとで `hashCI K s = hashV2c (wordsOf K) K.m.toNat (K.fin, K.finMid) (K.r.toNat : ZMod p) K.finLong s`
- **系 `hashCI_eps`**：正しい鍵（m は奇数、r < p、ほかは任意）を一様に選ぶと、違う 2 入力で
  Pr[`hashCI` が衝突] ≤ 2⁻⁶³ + (3N+1)/p。仕様の鍵集合 `keySet` との全単射（`keysOf` / `ofKeys`）で `v2c_eps` に帰着
- `#print axioms`：`hashCI_eq` は propext / Classical.choice / Quot.sound だけ。`hashCI_eps` はこれに加えて
  `xsr33_involutive` の `bv_decide` の公理（P1 の fmix64 全単射から来るもの。既存の `v2c_eps` と同じ）
- 詰まった所:
  - `congr 1` が `List.range (L/1024)` の等式で maxRecDepth → `congrArg (· ++ _)` と `List.map_congr_left` で書いた
  - Mathlib の `tsum`（無限和）と `Props.tsum` が衝突。`rw [tsum]` が Mathlib の方を拾った → `Props.tsum` と明示
  - `List.foldl_append` の `rw` が「`hornerK.retTy.denote` と `BitVec 64` が合わない」で失敗 → `change` で `hornerI` の形にしてから
  - **鍵の集合の membership で maxRecDepth**：`have h : p ∈ keySet := h1`（左右がまったく同じ型）でさえ失敗。
    `set_option diagnostics true` で `Fin.foldr.loop` が 540 回展開されていた（`Fin 130 → …` の全列挙を計算しようとしている）。
    `KeysI` の `Fintype` インスタンスを `@[irreducible]` にし、さらに `∈ keySet` / `∈ validKeys` は
    `mem_keySet_iff` / `mem_validKeys_iff` で**`rw` してから**使うことで回避（`exact` や `.mp` で型を照合させない）
- 全体の `lake build` は 19 秒（キャッシュ済みの Mathlib を除く）。新しいファイルの警告 0

### 参照実装を実行して Rust と突き合わせる（`lake exe ref_vectors`）

- `LeanHash/Impl/RefMain.lean`（Mathlib なし）：splitmix64 と `Keys::from_seed` を Lean に写し、seed 4 種 × 長さ 70 種（0..=40、
  経路と端数の境界 63〜129、1016〜1040、2047〜2057、3000、3072、3073、4096、5000）＝ 280 本を `seed len hash` で出力
- 実行は 1.9 秒（`List.getD` の O(n) 読みだが、長い入力はブロックに `drop` / `take` してから読むので速い）
- Rust 側 `v2::lean_ref::matches_lean_reference`：同じ鍵・入力を作って `hash_c` と比べる。ベクトルは `include_str!`
- 結果: **280 本すべて一致**。`cargo test -p leanhash`（debug）、`--release`、`RUSTFLAGS="-C target-cpu=native" --release`（AVX2 版のブロック和）のどれも 26 passed
- テストが違いを拾うかの確認（Rust を 1 か所ずつ壊して戻す）: 端数の読み `rem.max(8)` → `rem.max(16)`、
  33..=1024 の長さレーンの鍵 129 → 128、1〜3 バイトのシフト 8 → 9 のどれも `matches_lean_reference` が失敗した

## 決めたこと

- 外側の処理は「Lean の参照実装（核の `Kernel.run` を `List.foldl` で回す）＝ 仕様」を定理、「参照実装 ＝ Rust」を差分テストにする。
  IR にループの文を入れて外側まで Rust を生成する案は、今は取らない（SIMD と外側のスライス操作は Rust で書く方が自然で、
  形式的なつなぎは P3.5 の Aeneas に任せる）
- 参照実装は Mathlib なしのファイルに置き、実行できる形を保つ（差分テストのベクトルの出どころが、仕様と一致を証明した関数そのものになる）
- 鍵の有限集合 `KeysI` の `Fintype` は `@[irreducible]`。集合の membership は `rw` で条件に開いてから使う
