## 試したこと

### HashIR（`LeanHash/IR/Syntax.lean`、`Semantics.lean`）

- 型は u64 / u128 だけ。式 `Expr : Ty → Type`（変数、定数、`+ - *`（wrapping）、`^ & |`、定数シフト、`as u128`、`as u64`、`if a < b {x} else {y}`）
- 核（`Kernel`）は「引数 → `let` の並び → 戻り値」の直線型。ループ・関数呼び出しはまだない（`reduce` を `mulmod` / `horner` の中で使うのは、Lean 側で文の並びを返す関数 `reduceStmts` / `mulmodStmts` を展開して作る）
- 意味論は `BitVec`。環境は型ごとの「名前 → 値」（`Env` に `v64` / `v128`）。依存型のキャストを避けるため、1 つの関数 `(t : Ty) → String → t.denote` にしなかった
- 整形性 `Kernel.wf`（Bool）：シフト量 < 幅、定数 < 2^幅、変数は定義済みで最後に束縛された型と同じ。Rust の `let` は名前を覆い隠すので、同じ名前を別の型で束縛し直したあと古い型で読むと意味論とずれる。それを `List.lookup` で禁止した（最初は `contains` で書いていて、この穴に後で気づいた）
- `kernels_wf : kernels.all Kernel.wf = true := by decide` が通る
- 行き止まり（すぐ直った）: `Xor` クラスはない（`XorOp`）。`Ty.ofNat` は `Ty` に自動で生える名前とぶつかった（`Ty.lit` に改名）

### 核（`LeanHash/Impl/Kernels.lean`）

試作の Rust と同じ計算・同じ順序で書いた: `fmix64`、`finish`（fmix64(pre ^ fin)）、`nh32_lane`、`nh_pair`、`reduce`、`mulmod`、`horner`、`ms`、`limb0` / `limb1` / `limb2`。

### eval = spec（`LeanHash/Impl/Equiv.lean`）

| 定理 | 内容 |
| :--- | :--- |
| `fmix64K_eq` | = `Spec.fmix64`（`simp` で意味論を開くだけ。`rfl` で閉じる） |
| `finishK_eq` | = `Props.out fin pre`（P2 の合成則で使った仕上げそのもの） |
| `nh32LaneK_eq` | `toNat` = `pairVal (lane32 v) (lane32 k)`（W = 2³²） |
| `nhPairK_eq` | `toNat` = `pairVal`（W = 2⁶⁴） |
| `reduceK_eq` | すべての u64 で x mod p（y = (x mod 2⁶¹) + ⌊x/2⁶¹⌋ ≤ 2⁶¹ + 6 < 2p なので前提なし） |
| `mulmodK_eq` | a, b < p で a·b mod p |
| `hornerK_eq` | h, r < p、**c < 2⁶³** で ZMod p の h·r + c |
| `hornerRun_eq` | 係数がどれも < 2⁶³ なら、`horner` の繰り返し = `Props.horner`（`List.foldl` の帰納法） |
| `msK_eq` | = `Props.ms 128 64` |
| `limbsK_eq` | 3 つの limb = `Props.limbs`（(x, y) を NH32×2 の出力として読んだもの） |

- `#print axioms`：どれも `propext` / `Classical.choice` / `Quot.sound` だけ（`bv_decide` も `native_decide` も使っていない）
- 方針: 乗算は `bv_decide` に渡さない（CLAUDE.md）。`toNat` に落とし、積 a·b は `generalize` で 1 つの自然数にして上界（< 2¹²²）だけを残し、`omega` で閉じた（mod / div は定数で割るものだけなので `omega` の範囲）
- 行き止まり:
  - `horner` の文の並びをそのまま `simp` で開くと、`y` を 3 回読むので部分式が複製され、ゴールが数百行に膨らんだ → 「文の並び → 名前付きの BitVec 関数（`yBV` / `redBV` / `sBV`）」の補題（`exec_reduceStmts` / `exec_mulmodStmts`）を先に示し、関数のまま環境に入れてから開いた。`toNat` の性質は関数ごとに 1 回だけ示す（`redBV_toNat`、`sBV_toNat`）
  - 自然数の AND マスク `x &&& 2305843009213693951` が `omega` に通らない → `Nat.and_two_pow_sub_one_eq_mod` を数値リテラルの形にした補題（`land_m61` など）で mod にする。`norm_num` が 2⁶¹ をリテラルにするので、補題の右辺もリテラルで書く必要があった
  - `"m" ++ "_t"` が簡約されず、変数の読み出しで `if "c" = "m" ++ "_t"` が残った → `String.reduceAppend` を simp 集合に足した
  - `if_pos` / `if_neg` が deprecated → `simp only [h, ↓reduceIte]`
- Equiv.lean の検査は 8 秒

### 前提 c < 2⁶³ について（気づいたこと）

- `horner` は `mulmod(h, r) + c` を 64bit で足すので、c ≥ 2⁶⁴ − p 付近で桁あふれする。仕様との一致は c < 2⁶³ を仮定した
- 試作では c に limb（< 2⁶⁰）と**入力長 L**（`horner(h, r, len)`）を渡している。L < 2⁶³ なら成り立つ（P2.5 の定理は L < p ≈ 2⁶¹ を仮定済みなので、その範囲ではつねに成り立つ）
- 差分テスト `horner_precondition_is_needed` で、c = u64::MAX では仕様とずれることを確かめた（前提が本当に要る）
- 手書きの `lib.rs` の `horner` は `+ c` が素の加算なので、debug ビルドだと c が大きいと overflow の panic になった（差分テストを debug で回して気づいた）。生成版は wrapping。比べるのは前提の範囲内だけにした

### EmitRust（`LeanHash/IR/EmitRust.lean`、`lake exe emit_rust`）

- 対応表（ファイル先頭のコメント）だけを信頼する: `wrapping_add/sub/mul`、`^ & |`、`<< >>`（k < 幅）、`as u128`、`as u64`、`if a < b`、`0x…_u64`
- 括弧: 式ごとに「演算子の式か」を返し、演算子の被演算子・メソッドのレシーバーに置くときだけ括弧で囲む（`x ^ (x >> 33)`、`(a as u128).wrapping_mul(b as u128)`）
- 実行ファイルは Mathlib を読まない（IR と Kernels だけ）。出力は 3 秒
- 出力 `rust/leanhash/src/kernel.rs` は `#[rustfmt::skip]`（生成器の出力をそのまま置く）
- 再生成と差分の確認: `lake exe emit_rust | diff - rust/leanhash/src/kernel.rs`（workshop の `emit-rust --check`、`check` にも入れた）

### Rust 側の切り替えと差分テスト

- `v2.rs` の `hash` / `hash_b` / `hash_c` の核（NH のレーン・組、Horner、limb、multiply-shift、仕上げ）を `kernel::*` に置き換えた。バイト読み、ブロックのループ、AVX2、経路の分岐は手書きのまま
- 切り替える**前**に、手書き版で `hash_c` / `hash` / `hash_b` の出力を畳み込んだ値を記録（鍵 4 種 × 長さ 0..=4200 と 8191, 8192, 8193, 65536, 100000）: `0x8c5d62ac59bb4b5b`（既定と `-C target-cpu=native` で同じ）→ 切り替え後のテスト `golden::matches_handwritten_kernels` で一致
- `kernel_diff.rs`：核ごとに手書き版（切り替えで消したものは写しを置いた）と、u128 で書いた仕様の両方と比べる。境界値（0, 1, p−1, p, p+1, 2⁶⁰, 2⁶¹, 2⁶³, u64::MAX など）＋乱数 20 万組ずつ
- 結果（`cargo test -p leanhash`）: 25 passed（release、debug、`RUSTFLAGS="-C target-cpu=native"` のどれも）。既存の `lean_spec_matches_hash_c` / `lean_spec_matches_hash_long` もそのまま通る

## 決めたこと

- HashIR は「型ごとの名前空間を持つ直線型 + 式の中の比較つき選択」から始める。ループは Lean 側では `List.foldl` で外から回し（`hornerRun_eq`）、IR の文にはまだしない
- Rust の生成物は crate に置いてコミットする（ビルドに Lean を要求しない）。ずれは `emit-rust --check` で見る
- `horner` の仕様は c < 2⁶³ の前提つきで述べる
