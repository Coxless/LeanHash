# P3.5 入口：Aeneas で外側のループを抽出し、Lean の参照実装と一致を証明できるか試す

## 目的

- CONCEPT の未解決の問い「Aeneas が外側処理（スライス操作、ループ）をどこまで抽出できるか」に、小さな例で答える
- 対象は `v2::nh32x2_partial` のスカラーのループ（スライス、`div_ceil`、最後のレーンの重ね読み）。
  抽出した Lean の関数が、仕様と一致を証明済みの参照実装 `nh32x2PartialI`（`LeanHash/Impl/Outer.lean`）と一致することを示せるか
- 詰まるなら、どこで詰まったか（抽出できない構文、Lean / Mathlib の版の衝突、証明の手間）を記録して、P3.5 の方針（Rust の書き方を変える / 差分テストとファジングで代替）を決める材料にする

## 環境

- クラウドセッション（LXD なし）。Intel Xeon @ 2.10GHz、4 vCPU
- Aeneas `698a336`、OCaml 5.3.0（`.workshop/versions.sh`）。Lean 4.35.0 / Mathlib v4.35.0（このプロジェクト）

### 抽出する Rust（`rust/leanhash/src/outer.rs`）

- `v2::nh32x2_partial` のスカラーのループを関数 `nh32x2_lanes(k, b, lanes, start, s1, s2)` に切り出した（`while`、スライスと配列の添字、`wrapping_add`）
- `rd64` は `u64::from_le_bytes(b[i..i+8].try_into().unwrap())` をやめ、8 バイトを OR とシフトで組む形にした（`try_into` / `from_le_bytes` のモデルがあるか不明なので、確実に抽出できる形を先に試す）
- `nh32x2_partial_scalar(k, b)`：レーン数 `(len + 7) / 8` で全レーン

### Charon → Aeneas

```sh
cd rust/leanhash
charon cargo --preset=aeneas --start-from leanhash::outer --dest-file $SP/extract/leanhash.llbc
aeneas -backend lean -dest $SP/extract/out $SP/extract/leanhash.llbc
```

- Charon は 0.6 秒。`cargo miri setup` がないという警告（標準ライブラリの full MIR を使えず、rustc の既定の sysroot にフォールバック）が出るが、抽出は成功
- Aeneas は 0.9 秒で `Leanhash.lean` を出力。`--start-from leanhash::outer` で、`outer` から呼ぶ `kernel::nh32_lane` も一緒に抽出された（AVX2 の unsafe コードは呼ばれないので対象外）
- 出力の形:
  - `while` ループは `loop` コンビネータ ＋ 本体 `outer.nh32x2_lanes_loop.body : … → Result (ControlFlow …)`
  - 添字 `Slice.index_usize` / `Array.index_usize`、`usize` の `+` `-` `*` は範囲外・オーバーフローで失敗しうる `Result`
  - `wrapping_add` / `wrapping_mul` / `&` / `|` はそのまま、シフトは `Result`（シフト量 ≥ 64 で失敗）
  - ファイルは `module` / `public import Aeneas`（Lean のモジュールシステム）

### Aeneas の Lean ライブラリをこのプロジェクトの依存に

- `lakefile.toml` に `[[require]] aeneas`（git、`subDir = "backends/lean"`、rev `5a392f4`）を足し `lake update aeneas`（3 分 48 秒。Mathlib は変わらず）
- `lake build Aeneas` は 8 秒（`preferReleaseBuild` で GitHub Releases のビルド済み olean を取ってきた）
- 生成コードを `LeanHash/Aeneas/Leanhash.lean` に置いた。`module` / `public import Aeneas` のファイルを、モジュールでない既存のファイルから import しても問題なし
- `lake env lean` で証明ファイルを確かめるのは、初回 2 分（Aeneas＋Mathlib の olean の読み込み）、2 回目からは 7〜8 秒

### 証明 `LeanHash/Aeneas/OuterProof.lean`

Aeneas のドキュメント（`documentation/skills/proof-patterns`、`aeneas-tactics-quickref`）のやり方に従った。仕様は Hoare 三つ組 `f ⦃ post ⦄`（失敗・発散しない＋結果が post）。

- `nh32_lane_spec`：`step*` のあと、`laneI` を `ir_simp` で開いた式（`laneI_eq`）に書き換えて `simp [*]`
- `rd64_spec`（`i + 8 ≤ L` で `r.bv = rd64I (bytesOf b) i`）：
  - `step*` が添字の範囲（スライスの切り出しと 8 回の添字）を全部片付けた。残りは「OR とシフトで組んだ値 = little-endian の和」
  - `or8_toNat`：`BitVec.toNat_or` / `toNat_shiftLeft` で Nat に落とし、`Nat.two_pow_add_eq_or_of_lt` を 7 回（`bv_decide` は使っていない）
  - 切り出し `c = b[i..i+8]` の要素は `List.getElem_slice` で `b[i + j]` に
- ループ `lanes_loop_spec`：`loop.spec_decr_nat`、尺度 `lanes − i`、不変条件「i ≤ lanes ∧ (残りのレーン range' i (lanes − i) の foldl) = 目標」。
  本体は `split`（`i < lanes`）→ `step*` → 中の `if i + 1 = lanes` を `split` → `step*`。読み出しの範囲と鍵の添字 `k[i]`, `k[i+1]`（< 130）は `step*` / `scalar_tac` で閉じた
- `nh32x2_partial_scalar_spec`：`div_ceil` の仕様（`x ⌈/⌉ 8`）→ `(L + 7) / 8`（`Nat.ceilDiv_eq_add_pred_div`）、`List.range_eq_range'` で参照実装の `laneLoop` と `rfl`
- `nh32x2_partial_scalar_nhT`：既存の `Impl.partial_nhT` とつないで、**Rust（抽出）の出力 ＋ 長さレーン ＝ 仕様の `nhT (eB …) (msgB …)`**
- `#print axioms`：どちらも propext / Classical.choice / Quot.sound だけ
- 詰まった所:
  - `step*` は中の `if` で止まる → `split` してから続ける
  - `step` が付ける名前が分かりにくい（`r1 r2`）→ `step as ⟨n, hn⟩`
  - `div_ceil` の前提（レーン数 = (L+7)/8）を `step*` が自動では示せない → `div_ceil` を `step as` で 1 つ進め、`have` してから次の `step`
  - 鍵の添字 `k.val[j]` と `getElem!` の橋渡しで `rw` が「motive is not type correct」→ `getElem!_pos k.val (j+1) h` と引数を明示し、残りを `simp only`
  - `UScalar.val` を `simp` に入れると `UScalar.bv_toNat` とループ（maxRecDepth）→ `rw` と `rfl` で

### Rust の本番コードを抽出した関数に切り替える

- `v2::nh32x2_partial` のスカラーのループを `crate::outer::nh32x2_lanes(k, b, lanes, i, s1, s2)` の呼び出しに置き換え
  （AVX2 があれば 4 の倍数より後のレーン、なければ全レーン）。これで検証した関数が本番の経路そのものになった
- `div_ceil`：clippy（`manual_div_ceil`）に合わせて `b.len().div_ceil(8)` に。Aeneas には `core.num.Usize.div_ceil` のモデルと `@[step]` の仕様があった
- **速度の失敗と修正**（`leanhash-bench --quick`、leanhash-v2c、Intel Xeon @ 2.10GHz・4 vCPU・rustc 1.97.0）:
  - 最初の `rd64`（`b[i] | b[i+1] << 8 | …` を b に直接）では、スカラー版（既定のターゲット）が大きく遅くなった:
    64B 14.8 → 24.7ns、512B 93.7 → 175.8ns、1KB 4.71 → 2.91 GB/s（添字の検査が 8 回残り、1 回の読み出しにまとまらない）。AVX2 版も 64B 10.7 → 16.8ns
  - `let c = &b[i..i + 8];` で先に切り出してから `c[0]…c[7]` を組む形に変更 → 元に戻った（Aeneas は `core.slice.index.Slice.index` と `Range` で抽出できた）

| 長さ | 既定（切り替え前 3 回） | 既定（切り替え後 3 回） | native（前） | native（後） |
| :--- | :--- | :--- | :--- | :--- |
| 64 | 14.8 / 13.8 / 14.9 ns | 14.1 / 13.9 / 14.6 ns | 10.7 ns | 10.1 ns |
| 128 | 23.6 / 25.8 / 24.9 ns | 28.9 / 23.9 / 25.2 ns | 12.6 ns | 11.9 ns |
| 512 | 93.7 / 85.5 / 81.6 ns | 84.8 / 82.7 / 84.0 ns | 24.3 ns | 24.8 ns |
| 1024 | 4.71 / 5.75 / 6.02 GB/s | 5.84 / 5.58 / 5.94 GB/s | 24.3 GB/s | 24.7 GB/s |
| 4096 | 9.62 / 9.99 / 9.71 GB/s | 6.09 / 8.92 / 9.09 GB/s | 20.0 GB/s | 20.4 GB/s |

  - 4096B は端数がなく変更した経路を通らない。後の 1 回目（6.09）は外れ値、残りも 1 割弱低いが、quick モードの揺れか配置の影響とみる（要再計測）
- テスト：`cargo test --workspace`（debug）と `-C target-cpu=native --release` で 26 passed（切り替え前の出力の畳み込み `golden`、Lean の参照実装のベクトル `lean_ref` も一致）。fmt / clippy（既定・native）も通る

## 結果（まとめ）

- CONCEPT の問い「Aeneas が外側処理（スライス操作、ループ）をどこまで抽出できるか」→ **このループの範囲では全部できた**:
  `while`、スライスの切り出し（`&b[i..i+8]`）と添字、配列 `[u64; 130]` の添字、`div_ceil`、`wrapping_*`、シフトと OR、
  別モジュールの関数呼び出し（生成した核 `kernel::nh32_lane`）。証明も Aeneas のタクティク（`step*`）で添字の範囲がほぼ自動で片付いた
- 証明でつながった鎖: Rust（`outer::nh32x2_partial_scalar`、本番のスカラー経路）→ 参照実装 `nh32x2PartialI` → 仕様 `nhT (msgB …)`

## 決めたこと

- Aeneas はソースからビルドせず、GitHub Releases の nightly バイナリを使う（クラウドでは opam が使えない）。rev は `5a392f4` に上げる
- 抽出の対象は `rust/leanhash/src/outer.rs` に集め、Aeneas の対応範囲の safe Rust で書く。本番（`v2.rs`）はそれを呼ぶ
- 生成した Lean（`LeanHash/Aeneas/Leanhash.lean`）はコミットする（`extract --check` でずれを見る。kernel.rs と同じ扱い）
