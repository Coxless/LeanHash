## v2c の長い経路（`rust/leanhash/src/v2.rs` の `hash_long_b` を読んで整理）

L > 1024。nb = ⌊L/1024⌋ 個の完全ブロックと、最後の 1 ブロック（計 N = nb + 1 個の NH 出力）。

| ブロック | NH32×2 にかける内容 |
| :--- | :--- |
| j < nb | バイト [1024j, 1024j+1024) の 128 レーン（鍵レーン i と i+1）。長さレーンなし |
| 最後 | rem = L mod 1024 > 0 なら末尾 max(rem, 8) バイトを `nh32x2_partial`（経路 B と同じ読み方）、rem = 0 ならデータなし。どちらも長さレーン (L の下位 32bit, 上位 32bit) をレーン 128 に足す |

- 出力 (x, y) は v = x + 2⁶⁴·y の 128bit。limb は v の 60bit ずつ: v mod 2⁶⁰、⌊v/2⁶⁰⌋ mod 2⁶⁰、⌊v/2¹²⁰⌋（8bit）。Rust の `(x>>60 | y<<4) & MASK`、`y>>56` と同じ
- h = Horner(r; limb₀, …, limb_{3N−1}, L) mod p（h₀ = 0）。r は [0, p) で一様（`from_seed` は棄却法）
- t = Σ y_j mod 2⁶⁴
- 出力 = fmix64(ms(m, h·2⁶⁴ + t) ^ fin_long)

## 証明の方針

- Pr[衝突] ≤ Pr_{K,r}[(h, t) が同じ] + 2⁻⁶³（multiply-shift、`card_compose`）
- Pr_{K,r}[h が同じ] ≤ Pr_K[係数列が同じ] + 3N/p
  - 係数列が違えば、差の多項式は 0 でなく次数 ≤ 3N → 根は 3N 個以下
    - 長さが同じ：係数列の長さが同じで中身が違う
    - 長さが違う：定数項（L）が違う（L < p を仮定）
  - 係数列が同じ ⇒ 長さが同じで全ブロックの NH 出力が同じ ⇒ 違いのあるブロック j で NH32×2 が衝突 → 2⁻⁶⁴（`nhT_eau`）
- 合計 ε ≤ 2⁻⁶⁴ + 3N/p + 2⁻⁶³ ≤ 2⁻⁶³ + (3N+1)/p（承認済みの目標の形）

## 試したこと

### p = 2⁶¹−1 が素数

- `lucas_lehmer_sufficiency 61 (by norm_num) (by norm_num)` で 6 秒（Mathlib の Lucas–Lehmer の norm_num 拡張）。試し割りは使わない

### 多項式段（`LeanHash/Props/Poly.lean`）

- `rpoly`：逆順の係数列（先頭が定数項）の多項式。`coeff_rpoly`（m 次の係数 = 列の m 番目）を先に示すと、次数の上界・同じ長さでの単射性・定数項の違いがすべて係数の話になった
- `horner_eq_eval`：Horner（先頭から h ↦ h·r + c）= 逆順の列の多項式の値（`List.foldl_eq_foldr_reverse`）
- `card_eval_eq_le`：違う 2 多項式（次数 ≤ n）の値が一致する点は n 個以下（`card_roots'`）
- **`horner_au`**：係数列 a ++ [c] と a' ++ [c']（a の長さ ≤ n）で、「長さが同じで違う」か「c ≠ c'」なら、衝突する r は n 個以下
- 一発で通った（6 秒）

### 長い経路の符号化（`LeanHash/Spec/Long.lean`）

- `msgL s j`：ブロック j のレーン。完全ブロックは `msgB (blk s j)` のレーン 128 を消したもの、最後は `msgB (tail s)` のレーン 128 を長さレーンにしたもの
  - 経路 B の `msgB` / `msgB_inj` / `msgB_isSome` を切り出した列（`List.drop` / `take`）にそのまま使えた。オフセットを直接書くより短い
- `msgL_inj`：同じ長さ（> 1024）で全ブロックのレーンが同じならバイト列も同じ。バイト i が完全ブロックにあればそのブロック、なければ末尾（max(rem, 8) ≥ rem なので必ず覆う）
- 行き止まり: `set L := s.length` の後で `rw [hlen]` が `tailLen (List.length s)` の中の L を見つけられなかった → `congrArg tailLen hlen` で直接

### 長い経路の ε（`LeanHash/Props/Long.lean`）

- `limbs_inj`：limb 3 つ（ZMod p に入れたもの）から (x, y) が決まる。どの limb も 2⁶⁰ 未満 < p なので cast は単射。v = l₀ + 2⁶⁰·l₁ + 2¹²⁰·l₂ は `Nat.div_add_mod` 2 回
- `card_two_stage`：`card_compose` の一般形（2 段目の鍵の型が任意の Fintype）
- `card_polyH`：Pr_{K,r}[h 衝突] ≤ Pr_K[長さが同じで係数列が同じ] + 3N/p。長さが違えば定数項 L が違う（L < p を仮定）
- `card_coefs_eq`：違う 2 入力で「長さが同じで係数列が同じ」になる鍵は 2⁻⁶⁴ 以下。違いのあるブロック j を `msgL_inj` の対偶で取り、`exists_lastDiff` → `nhT_eau`
- `long_ratio`：確率の足し算。鍵の総数は変数のまま（P2 の教訓。展開させない）
- **`long_eps`**：1024 < L、L, L' < p、s ≠ s' なら Pr_{K,r,m}[衝突] ≤ 2⁻⁶⁴ + 3N/p + 2⁻⁶³（N = max(⌊L/1024⌋+1, ⌊L'/1024⌋+1)）
- `long_eps_le_target`：≤ 2⁻⁶³ + (3N+1)/p（2026-11-08 に承認した目標の形そのもの）
- `#print axioms long_eps` → `[propext, Classical.choice, Quot.sound]`
- 行き止まり（どれもすぐ直った）:
  - `omega` が `P61`（abbrev）の値を知らない → `ha.trans_le (by norm_num)`
  - `omega` に 2¹²⁷ を含む不等式を渡したら `maximum recursion depth` → `Nat.add_le_add_right` で明示
  - 一般の補題に `[DecidablePred fun p => C p.1 p.2]` を別引数で取ったら、`sum_product` 後の `ite` のインスタンスが食い違って calc が通らない → 引数から外し、`[∀ K, DecidablePred (C K)]` から作らせた
  - P2 と同じく linter `constructorNameAsVariable` が recursion depth で落ちる定理があり、その定理だけ切った
  - `push_neg` は deprecated（`push Not` に）

### 仕様と Rust の一致（`rust/leanhash/src/v2.rs` の `lean_spec_matches_hash_long`）

- Lean の `msgL` → `outL` → `limbs` → `polyH` / `tsum` → ms → fmix64 を Rust のテストに素朴に写し、`hash_c` と比べた（L = 1025〜1100、ブロック境界の前後 2047〜3073、4096、5000、9000。鍵 3 種 × 各 2 入力）
- `cargo test -p leanhash --release`: 18 passed（既定と `RUSTFLAGS="-C target-cpu=native"`）
- テストが空振りしないことの確認: 仕様側の t を y ではなく x の和にしたら失敗した。長さレーンの上位 32bit を 0 にしても通る（テストの長さは < 2³² なので区別できない。ここは仕様の読みどおりで、テストでは確かめられていない）

### 全長で 1 本の定理（`LeanHash/Props/All.lean`）

- `hashV2c w m (fin, fin_mid) r fin_long s`：L ≤ 1024 なら `hash1K`、それ以外は `hashL (eB w) r m fin_long`
- 鍵の集合 `keySet`（`card_keySet`：分母がちょうど鍵の総数 |Words|·2¹²⁷·2¹²⁸·p·2⁶⁴ であること）
- **`v2c_eps`**：長さ < p の違う 2 入力すべてで Pr[衝突] ≤ 2⁻⁶³ + (3N+1)/p（N = max(⌊L/1024⌋+1, ⌊L'/1024⌋+1)）
  - 両方 1KB 以下：r と fin_long は関係しない → `le1K_eps`（2⁻⁶²）。N ≥ 1 なので 2⁻⁶² ≤ 2⁻⁶³ + 4/p
  - 両方 長い：鍵を (((K, r), m), (F, fin_long)) に並べ替えて（`card_regroup`、`Finset.card_nbij'`）`long_eps`
  - 片方だけ長い：ほかの鍵をどう固定しても衝突する fin_long は 1 個以下（`card_out_fin_le_one`、fmix64 の単射と XOR）→ 2⁻⁶⁴
- `#print axioms v2c_eps` → `[propext, Classical.choice, Quot.sound, xsr33_involutive._native.bv_decide.ax_1_5]`（最後は P1 の xorshift の `bv_decide`。`le1K_eps` と同じ）
- 行き止まり:
  - `field_simp` が `maximum recursion depth`（鍵の数の大きな数を正規化しにいった）→ 変数だけの約分補題 `ratio_short` / `ratio_long` に出した（P2 と同じ対処）
  - 述語を `fun p => Q p.1` の形に `filter_congr` で書き換えてから `filter_product_left` で `rw` しようとしたら、`DecidablePred` のインスタンスが合わず rewrite が見つからない → 集合の等式を `ext` と `simp only [mem_filter, mem_product, …]` で直接示した（メンバーシップの段階ではインスタンスは関係しない）

## 決めたこと

- 長い入力の ε の主張は `long_eps`（2⁻⁶⁴ + 3N/p + 2⁻⁶³）とその上界 2⁻⁶³ + (3N+1)/p。全長をまとめた主張は `v2c_eps`
- 仮定 L < p（約 2.3 EB）は定理に明示する。これより長いと長さの係数 L mod p がぶつかりうる（Rust の `horner` も L < 2⁶⁰ 程度を前提にしている）
- N は「NH の出力の数」= ⌊L/1024⌋ + 1（端数がなく L が 1024 の倍数でも、長さレーンだけのブロックが 1 つある）。CONCEPT の (3n+1)/p の n はこれ

## 未解決・気づいたこと

- 仕様（Lean）と Rust の一致はまだテストだけ（P3 の `eval fast = spec` で埋める）。長さレーンの上位 32bit（L ≥ 2³²）はテストで確かめられていない
- 多項式の次数が N に比例するので、ε は 1 TiB（N ≈ 2³⁰）で約 2⁻²⁹（3·2³⁰/2⁶¹ ≈ 2⁻²⁹·⁴）。これは多項式 mod 2⁶¹−1 の構成の限界で、PolymurHash と同じ型。これより良くするなら木構造や大きい素数が要る（今は検討しない）
